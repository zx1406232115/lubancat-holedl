## 第 1 轮：空洞机制

**我的提问**

> 这个「空洞文件」到底是怎么实现的？怎么保证未写入的区域不占磁盘块？

**AI 产出**

结论：用 `ftruncate()` 而不是 `fallocate()`。

- `ftruncate(fd, size)` 只修改 inode 的 `i_size`，内核**不分配数据块**；
- `fallocate()` / `posix_fallocate()` 会真的预分配物理块，`st_blocks` 立刻上来；
- 自己 `write()` 一堆 `0` 撑大文件同样会占满磁盘。

并给出验证口径：`ls -l`（逻辑大小）对 `du`（实际占用），
真正的占用字节数是 `st_blocks × 512`。

**我的处理：采纳，但改掉一处错误**

这段是作业的核心，方向正确。但 AI 有一句说错了：它称 `ftruncate` 之后
「读出来是随机数据」。Linux 读空洞**返回全 0**，这是空洞的定义性质之一。
我在测试 1 里专门加了一条断言把这个性质钉死。

另外 AI 同时给出反例（`fallocate`、写零）这一点很有价值，
我把它作为注释写进了 `src/sparse.c` 顶部，答辩时可以直接引用。

## 第 2 轮：定点写的系统调用选型

**我的提问**

> 作业要求写「lseek + write 定点写入」，我该用哪一组系统调用？

**AI 产出**

建议 `pwrite()`：

- `pwrite(fd, buf, len, offset)` 语义上等价于
  `lseek(fd, offset, SEEK_SET)` + `write(fd, buf, len)`；
- 但 `pwrite` **不修改文件偏移量这个共享状态**，因此原子性更好、
  多线程共享 fd 时不会互相踩偏移，还少一次系统调用。

**我的处理：采纳**

作业文字写的是 `lseek + write`，我一开始担心用 `pwrite` 属于「没按要求做」。
权衡后认为：这道题考的是**「定点写、不破坏其它空洞」这个能力**，
而不是 API 名字，`pwrite` 是同一能力更严谨的表达。
而且 `lseek` 我并没有丢掉 —— `status --map` 里的空洞判定正是用
`lseek(fd, off, SEEK_DATA/SEEK_HOLE)` 实现的，文件偏移操作这个知识点仍然覆盖到了。

代码里把两者的等价关系写在 `sparse_write_at()` 的注释里，便于答辩解释。

顺带一个容易踩的坑（AI 主动提示）：`st_blocks` 的单位固定是 **512 字节**，
和 `st_blksize`（最优 IO 大小，通常 4096）完全不是一回事。

## 第 3 轮：断点续传的状态设计

**我的提问**

> Ctrl-C 之后怎么保证已下载的部分不白下？进度存在哪？

**AI 产出**

方案：`<输出文件>.holedl.state` 文本文件，存源标识 + 总大小 + 分块大小 + 进度位图。
两个关键点：

1. **每块完成立刻落盘**（`state_save()` + `fdatasync()`），而不是全部下完再写 ——
   `SIGINT` 会直接终止进程，攒到最后写等于没写；
2. **先写 `.tmp` 再 `rename()`** —— `rename` 在同一文件系统内是原子的，
   即使正好在写状态文件时被中断，也不会留下半个损坏的文件。

**我的处理：采纳，并追加一项**

这两点站得住。但我追加了一个要求：**续传必须校验数据正确性**。
位图只能说明「这块写过了」，不能说明「写对了」。
所以最终加了 `holedl verify` 子命令做逐字节比对，测试里也用它来判定续传是否真的成功。

## 第 4 轮：代码审查

**我的提问**

> 让 AI 审查自己刚生成的代码，找出 ≥3 处缺陷

**AI 产出**

找出并修复 5 处真实缺陷，其中 3 处会导致错误结果：

| # | 缺陷 | 严重度 |
|---|---|---|
| 1 | `usage()` 格式串 11 个 `%s`，只传了 10 个参数 | 中（未定义行为） |
| 2 | HTTP 头部解析**就地改写接收缓冲区**，破坏响应体首字节 | **高（数据损坏）** |
| 3 | `state_save()` 非原子写，中断时状态文件可能损坏 | 中 |
| 4 | 测试用 `tr -d '0'` 判断空洞，会把 `0x10` 里的 0 也删掉 | 中（测试假失败） |
| 5 | HTTP 测试用 `python3 -m http.server`，它不支持 Range | 中（测试无效） |

**我的处理：全部采纳**

这轮价值最高。三点说明：

1. **第 2 条最隐蔽**。它只在「HTTP 头部和 body 落在同一次 `recv()` 返回」时触发。
   本地小文件必现、真实网络偶发。若不审查，大概率潜伏到答辩演示才暴露。
   根因是 `strtok_r` 会在 token 末尾写 `'\0'`，而 body 就紧跟在头部缓冲区之后。
   修法是先把头部区域拷进独立 `scratch` 缓冲区再切分，原始缓冲区只读。

2. **第 4、5 条是它审自己的测试代码审出来的**。第 5 条尤其关键：
   原「HTTP 断点续传」测试其实是**无效测试** —— 服务器根本不支持 Range，
   测试却报通过。这种「测试假装通过」比没有测试更危险。

3. **第 1 条是编译器抓到的**。修复后我把「编译零警告」定为验收标准。

详细的现象 → 根因 → 验证见 `03-AI代码审查记录.md`。

## 第 5 轮：测试设计

**我的提问**

> 怎么证明断点续传真的有效？我不想只是「看起来能跑」

**AI 产出**

提出**伪造「下到一半」现场**的测试法：

```bash
head -c 1572864 /dev/urandom > src.bin     # 已知内容的源
./holedl create out.bin 1572864            # 同样大小的空洞文件
dd if=src.bin of=out.bin bs=256K count=3 conv=notrunc 2>/dev/null   # 灌入前 3 块
printf 'HOLEDL1\n%s\n%s\n262144\n%s\n' "$SRC" "$SIZE" "$HEX" > out.bin.holedl.state
./holedl download "$SRC" out.bin --block 256K    # 执行续传
./holedl verify "$SRC" out.bin                   # 逐字节校验
```

**我的处理：采纳，并扩展 4 条**

这个思路好，因为把「中断」从不可复现的手工操作变成了**确定性事件**。
我在此基础上补了：

- 测试 3：多次在不同偏移写入，验证**旧数据不被覆盖**（只测一次写不够严谨）；
- 测试 6：验证部分下载的文件「实占 < 逻辑大小」，即空洞机制在下载场景同样成立；
- 测试 7c：用**故意不支持 Range 的服务器**验证降级路径；
- 新增 `tests/range_server.py`（支持 `Range` + `HEAD` + 可限速），
  否则 HTTP 续传根本没法自动化验证。

最终 31 项断言全部通过。

## 第 6 轮：上板实测中发现并定位的缺陷 ⭐

这轮没有 AI 参与产出，是我在真机上跑出来的。

### 现象

在板子上做「限速下载 → 杀进程 → 续传」的真实演示时，日志出现矛盾：

- 断点状态文件明明正确写入了（`f8000000`，表示前 5 块完成）；
- 但重跑同一条命令时却打印 `── 全新下载：共 32 块`，**从第 1 块重新开始**。

而单元测试里的续传用例（测试 5、7）**全都是通过的**。

### 定位过程

关键在于那个反直觉的点：**为什么测试能过、真机却失败**。

沿着「测试通过但真机失败」这条线，我把可疑范围收敛到
「块数」这个差异上：测试用的文件是 1.5MiB / 256KiB = **6 块**，
而演示用的是 32MiB / 1MiB = **32 块**。

于是直接检查状态文件的位图长度：

```
hex = [ff80]  length = 4   expected length = 8
```

写出来 4 个 hex 字符，读的时候却期望 8 个。

### 根因

`state_save()` 和 `state_load()` 对同一份位图用了**两套不同的编码规则**：

| | 规则 | 32 块时的长度 |
|---|---|---|
| 写入方 `state_save` | 按**字节**存，每字节 8 位 → 每字节输出 1 个 hex 字符 | `(32+7)/8` = **4** 字符 |
| 读取方 `state_load` | 按**半字节**算，每 4 个块 1 个 hex 字符 | `(32+3)/4` = **8** 字符 |

`fread` 只读到 4 个字符，小于期望的 8 个 → 被判定为「状态文件不完整」→
**静默退化成全新下载**。

块数 ≤ 16 时两个公式**恰好相等**（都是 4），所以单元测试永远碰不到；
一旦块数超过 16 就必然失败。更隐蔽的是失败方式：它不报错，
只是安静地从头重下 —— 如果没有在真机上按真实规模跑一遍，这个 bug 不会被发现。

### 修复

统一成一种编码，并把编解码抽成一对函数（`bitmap_encode` / `bitmap_decode`），
长度一律按 `(nblocks+3)/4` 计算，字符内高位对应编号小的块。

同时在 `state_save()` 里加了一条**往返自检**：编码后立刻解码回另一个缓冲区，
与原始位图逐字节比对，不一致就放弃保存并报错。这样即使将来有人只改了编码方，
也会立刻在保存阶段失败，而不是等到续传时静默失效。

### 验证

- 新增回归测试 **5c**，专门覆盖块数 > 16 的情况
  （48 块、已完成 20 块，位图 `fffff0000000`）：通过；
- 真机重跑中断+续传演示：

```
── 发现断点状态：共 32 块，已完成 5 块，待续传 27 块
   [  6/32] 下载块…… ok          ← 从第 6 块继续
✔ 校验通过（33554432 字节）
sha256(source) = 37b80ddf…6412b
sha256(target) = 37b80ddf…6412b   ← 一致
```

**这轮的教训**：单元测试的**数据规模**本身是测试设计的一部分。
用例全部通过不等于功能正确 —— 如果所有用例都落在同一个「幸运区间」里
（这里就是块数 ≤ 16），缺陷会完整地穿过去。所以真机测试必须按**真实规模**来跑。

## 第 7 轮：平台适配（x86 开发机 → aarch64 开发板）

**我的提问**

> 程序要在 RK3566 的 aarch64 板子上跑，怎么编译和部署？

**AI 产出**

判断：空洞、`pwrite`、`ftruncate`、`SEEK_DATA` 都是 POSIX/Linux 通用能力，
**与 CPU 架构无关**，所以可以在开发机上先把功能与逻辑验证到位，
板子上用**原生 gcc** 编译即可，不必折腾交叉工具链。
`Makefile` 保留 `CROSS_COMPILE` 入口备用。

另提示两点：空洞依赖**文件系统支持**（ext4 可以，某些 FAT/exFAT 不行）；
`download` 除了 `http://` 还应支持**本地文件路径**，便于脱网验证。

**我的处理：采纳**

这个判断让工作重心放对了：先把逻辑和测试做扎实，再上板。
实际执行时我也确实用交叉编译先确认了一遍「源码能在 aarch64 上干净编译」，
再到板子上做原生编译和实测 —— 一次通过，没有出现编译层面的问题。

**落地产物**：`Makefile` 的 `CROSS_COMPILE` 支持；
`src/download.c` 的本地源分支（测试 5、7 均覆盖）。

## 我对 AI 产出的两次否决

### 否决 1：用「写零撑大文件」来演示空洞

**AI 初版方案**：先 `open` 再 `write` 一堆 `0x00` 把文件写到 128MB，
称「这些 0 就是空洞」。

**否决理由**：这是**概念性错误**。写进去的零是**真实占块的数据**，
`st_blocks` 会等于逻辑大小，`du` 会显示 128MB。
真正的空洞是**内核根本没有为这段区间分配块**，读的时候才由内核合成 0。
两者在「读出来都是 0」上相似，但在**磁盘占用上完全不同**——
而磁盘占用正是这道题要考察的核心。

**最终做法**：只用 `ftruncate()`，并把 `fallocate` 和「写零」写成反例注释。

### 否决 2：只支持 HTTP，不做本地文件源

**AI 初版方案**：`download` 只接受 `http://` URL。

**否决理由**：演示现场网络不一定可靠，而考察点是「空洞 + 续传」本身，
不该被网络问题干扰。支持本地文件源可以让核心逻辑**完全脱网验证**，
风险低得多，也能让测试不依赖外部服务。

**最终做法**：`download` 同时接受 `http://` 和普通文件路径，
两条路径共用同一套「空洞创建 + 位图状态 + 定点写」逻辑。

## 小结

| 维度 | 情况 |
|---|---|
| 有效协作轮数 | 7 轮 |

| 否决 | 2 处设计性错误（写零造空洞、只支持 HTTP） |

**两点体会**

1. **AI 产出的正确性需要独立验证。** 它写得快，但表达得同样自信，
   两者不成正比。第 1 轮里「空洞读出来是随机数据」就是一例 ——
   说法听起来合理，实际与 Linux 行为相反。

2. **测试通过 ≠ 功能正确。** 第 6 轮那个缺陷，31 项断言全绿也照样存在，
   因为所有用例都落在块数 ≤ 16 的「幸运区间」。
   真正把它挖出来的是**在真实硬件上、按真实规模跑一遍**。
   这也是这个作业要求「板端运行截图」的意义所在 ——
   板端跑的不是形式，它确实能发现开发机上发现不了的问题。
